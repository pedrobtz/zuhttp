# zuhttp correctness review — Mistral Vibe, session 2

A correctness-focused review of the R package `zuhttp` and its C core under `src/`,
including a re-verification of every finding recorded in the earlier `review.md`
(written against checkout `90832db`) against the current tree (branch `main`).

Goal per instructions: correctness bugs only — code that compiles and "works" on
simple input but can return wrong results, crash R, or corrupt memory. Style,
performance and documentation are out of scope.

## How this review was done

- Full read: `src/init.c` (the R boundary), every shipped `zuh_*.c` file
  (alloc, buffer, error, time, stream, headers, request, framing, response, uri,
  redirect, inflate, net, tls, tls_nw, engine, fork, pool, sink, body, trace,
  proxy, redact, h2, tls_openssl, tls_schannel), the vendored patch sites
  (nghttp2, picohttpparser, uriparser), `src/Makevars{,.win}.in`, `NAMESPACE`,
  and the entire R layer.
- Machine-checked baseline: the offline R suites, the live network/pool/download/
  interrupt/certs suites (`ZU_TEST_NETWORK=1`), and the full live HTTP/2 suite
  against `tools/h2-test-server.py` (hypercorn + `h2`, an implementation
  independent of the vendored nghttp2). All pass except one flake caused by
  `badssl.com` refusing connections (`test-http2.R:104`) — an external-host
  dependency, not a package bug.
- Fuzzing: 33,000 mutated inputs across the 11 fuzz corpora under
  ASan/UBSan — zero reports. `ctest` passes (2,526 checks, allocation-balance
  oracle clean).
- Reproduction probes (all findings below were re-reproduced on the *current*
  tree, via a raw byte-scripted loopback server, the local h2c server, and
  pure mock transports where no network was needed).

Severity classes: `crash` | `wrong-result` | `memory-safety` | `robustness` | `portability`.

## A. New findings (not in `review.md`)

### A1. HTTP/1.1 uploads whose body is between ~32 KiB and 64 KiB are sent TWICE

- SEVERITY: wrong-result (wire corruption)
- LOCATION: `src/zuh_engine.c:1182-1192`
- TRIGGER (reproduced, exact byte counts from a loopback socket server):
  ```r
  big <- as.raw(rep(0x41, 40000))
  zu_post("http://127.0.0.1:PORT/u", body = big, check = FALSE)
  ```
  The server observed `Content-Length: 40000` and **80,000 body bytes on the
  wire** (2x the body). Sizes 10,000 / 20,000 / 30,000 / 70,000 send exactly
  once; 40,000 doubles.
- WHY: `zuh_buf_append(&wire, body, body_len)` is evaluated *inside* the first
  `if` condition, and on success it grows `wire.len` from ~152 to ~40,152.
  The adjacent `else if` then re-evaluates `body_len > wire.max - wire.len`
  (now `40000 > 65536 - 40152 = 25384`, true) against the *already-grown*
  buffer, so the body that was appended is written **again** as a separate
  `write_all()`. The trigger window is: `wire.len + body_len <= 65536`
  (append succeeds) **and** `wire.len + 2 * body_len > 65536` — i.e. mid-size
  in-memory uploads, exactly the size a real API JSON payload has.
  Consequences: the duplicated bytes are parsed by the server as a second,
  garbage request on the connection; the extra copy survives connection reuse
  and proxies; and the §35.3 trace reports `sent_bytes` as `wire.len +
  body_len` (40,152), not the 80,152 actually sent.
  This is the same finding as `review.md` round 1, item 1 — **still present**,
  and it is the most severe issue in the package.
- FIX (minimal, no side effects in conditions):
  ```diff
  --- a/src/zuh_engine.c
  +++ b/src/zuh_engine.c
  @@ -1182,12 +1182,13 @@
               sent_bytes = wire.len + body_len;
  -            if (rc == ZUH_OK && body_len > 0 && body_len <= wire.max - wire.len &&
  -                !zuh_buf_append(&wire, body, body_len)) {
  -                zuh_error_set(err, ZUH_ERR_NOMEM, ZUH_PHASE_NONE, "out of memory");
  -                rc = ZUH_ERR_NOMEM;
  -            } else if (rc == ZUH_OK && body_len > 0 && body_len > wire.max - wire.len) {
  +            if (rc == ZUH_OK && body_len > 0 && body_len <= wire.max - wire.len) {
  +                if (!zuh_buf_append(&wire, body, body_len)) {
  +                    zuh_error_set(err, ZUH_ERR_NOMEM, ZUH_PHASE_NONE, "out of memory");
  +                    rc = ZUH_ERR_NOMEM;
  +                }
  +            } else if (rc == ZUH_OK && body_len > 0) {
                   if (!zuh_stream_write_all(s, wire.data, wire.len, total, err))
                       rc = err->code ? err->code : ZUH_ERR_IO;
                   else
  ```
- CONFIDENCE: high — reproduced with exact byte counts (a two-connection-free,
  deterministic binary-counting server). Confirmation test: POST bodies at
  30,000 / 40,000 / 60,000 / 70,000 bytes against a byte-counting server; each
  must arrive exactly once, and the 40,000 case fails today.

### A2. `redirects` above `.Machine$integer.max` silently disables redirect following

- SEVERITY: wrong-result
- LOCATION: `R/perform.R:111` (`as.integer(p$redirects)`), validation gap at
  `R/perform.R:309-314`; consumed at `src/init.c:867` (`Rf_asInteger`) and
  every `o->max_redirects > 0` test in the engine.
- TRIGGER (reproduced): against a 302 scripted server,
  `zu_get(url, redirects = 1e10)` — or `redirects = 2147483648` — returns the
  **302 response itself** to the caller, with only an R coercion *warning*
  ("NAs introduced by coercion to integer range"). The caller asked "always
  follow"; they got "never follow", silently.
- WHY: `as.integer(1e10)` is `NA_integer_`; `init.c` stores it, and NA
  (`INT_MIN`) reads as *smaller* than 0, the "disabled" sentinel.
  `zu_pool()` guards exactly this case with `x > .Machine$integer.max`
  (`R/pool.R:59-72`, with a comment explaining why); `redirects` was missed.
- FIX:
  ```diff
  --- a/R/perform.R
  +++ b/R/perform.R
  @@ -309,7 +309,8 @@
     if (
       !is.numeric(policy$redirects) ||
         length(policy$redirects) != 1L ||
         is.na(policy$redirects) ||
  -      policy$redirects < 0
  +      policy$redirects < 0 ||
  +      policy$redirects > .Machine$integer.max
     ) {
  ```
- CONFIDENCE: high — reproduced (302 returned, warning shown).
  Test: a scripted 302 with `redirects = 1e10` must `stop()`, and
  `.Machine$integer.max` must still follow.

### A3. `zu_retry(attempts = <above integer range>)` breaks EVERY request on the client

- SEVERITY: wrong-result (invalid policy silently accepted; every request dies)
- LOCATION: `R/retry.R:57-68` (validation) and `R/retry.R:78`
  (`attempts = as.integer(attempts)`); NA poisons `R/perform.R:489`
  (`may_replay <- policy$attempts > 1L && ...`) and `R/perform.R:517`.
- TRIGGER (reproduced, no network needed):
  ```r
  ok <- zu_mock_transport(function(req) zu_response(200L, body = "yes"))
  cl <- zu_client(transport = ok, retry = zu_retry(attempts = 1e10))
  zu_get("http://example.test/x", client = cl)
  # Warning: NAs introduced by coercion to integer range
  # Error: "missing value where TRUE/FALSE needed"
  ```
  Every request through that client fails this way — including successful ones.
  `.Machine$integer.max` works exactly, so the boundary is `attempts > 2^31-1`.
- WHY: same class as A2. `as.integer(1e10)` is NA; `NA > 1L` is NA; `&&` with
  a TRUE right side yields NA; `if` on NA errors deep inside the retry loop,
  far from the user's `zu_retry()` call.
- FIX: add `attempts > .Machine$integer.max` to the check in `R/retry.R:57-66`,
  mirroring `zu_pool()`'s `check_count()`.
- CONFIDENCE: high — reproduced with a pure mock transport.
  Test: the trigger above must `stop()` at `zu_retry()` construction.

### A4. `max_chunk` in the chunked decoder is dead code in production

- SEVERITY: robustness (dead guard; not currently triggerable from R)
- LOCATION: `src/zuh_response.c:106` (`zuh_chunked_init` takes `max_chunk`),

### B1. (R1-2) Fork + open streamed body leaves both processes with a broken body

- SEVERITY: memory-safety / wrong-result (cross-process socket use)
- LOCATION: `src/zuh_engine.c` `struct zuh_open_body` (~line 780) has no owner
  PID; `zuh_net.c` `net_impl` has none either (only `nw_impl` on the
  Network.framework backend does, via `m->pid`).
- TRIGGER (reproduced, current tree): open a streamed body over local h2c
  (`GET /slow`), read 4 bytes, then fork with `parallel::mcparallel()` and
  call `zu_resp_read()` in the child, then read again in the parent.
  Result: the child's read returns immediately with 0 bytes (rather than
  waiting as the parent's reads do), the child's exit finalizers act on its
  copy of the external pointer — closing the *parent's* socket from the
  child — and the parent's follow-up read raises `zu_io_error`. The parent's
  response is permanently broken the moment a forked child touches or collects
  it.
- WHY: the pool's §26.4 fork guard protects *pooled idle* connections
  (`zuh_pool_check_fork`), but a connection checked out into an open response
  body is invisible to it; nothing on the `zuh_open_body` or `zuh_stream`
  records *which* process created it. The macOS/Network.framework fork
  hazard is guarded elsewhere in exactly the way this path lacks.
- FIX: record the creating PID on `zuh_open_body` and refuse (or
  leak-and-error) inherited reads, aborts and finalizers, the way
  `zuh_net.c`'s `net_impl` should and `zuh_tls_nw.c`'s `nw_impl` already does.
- CONFIDENCE: high that the cross-process breakage occurred (observed);
  medium that the precise mechanism is the child's finalizers rather than the
  raw child read — a valgrind/ASan run or an FDclose trace would confirm.

### B2. (R1-4) Repeated `Content-Encoding` headers silently mis-decode

- SEVERITY: wrong-result
- LOCATION: `src/zuh_body.c:28` (parses only the first `Content-Encoding`)
  and `src/zuh_body.c:45` (then removes *all* `Content-Encoding` headers).
- TRIGGER (reproduced): a chunked response with two `Content-Encoding: gzip`
  fields and a body that is `gzip(gzip("hello world"))` returns the
  *still-compressed* inner gzip stream (32 bytes, `1f 8b` magic) as the final
  body, with every `Content-Encoding` header removed — the caller silently
  receives bytes that are not what the headers now claim.
- WHY: RFC 9110 stacks encodings; two `gzip` fields mean "decode gzip twice".
  The client decodes once, then erases the evidence. Since stacked decoding is
  deliberately unsupported (§21.4 refuses `gzip, br` *values*), the multi-*field*
  case should be refused the same way, not silently under-decoded.
- FIX (minimal): in `zuh_body_pipe_init`, if
  `zuh_headers_count(h, "Content-Encoding") > 1`, raise
  `ZUH_ERR_BODY_DECODE` ("stacked Content-Encoding is not supported")
  before decoding.
- CONFIDENCE: high — reproduced byte-for-byte.
  Test: the trigger above must raise; `Content-Encoding: gzip` alone with
  `gzip(x)` must still decode.

### B3. (R1-5) `max_body` binds decoded bytes under Content-Length framing but wire bytes under chunked framing

- SEVERITY: wrong-result (inconsistent limit semantics)
- LOCATION: `src/zuh_body.c:133` (`zuh_chunked_init(&r->dec, 0, max_body)`)
  plus `src/zuh_response.c:210-218` (applies that budget to the *de-chunked,
  still compressed* bytes), versus the Content-Length path where
  `cap_check()` (`src/zuh_body.c:65-73`) and `zuh_inflate` bound *decoded*
  output only.
- TRIGGER (reproduced): the same gzip stream (decodes to exactly 5 bytes) with
  `max_body = 5`:
  - `Content-Length` framing: succeeds, body `"hello"`.
  - `Transfer-Encoding: chunked` framing: raises `zu_body_limit_error`.
  Equivalent responses, opposite outcomes.
- WHY: under chunked framing the compressed payload (25 wire bytes) is
  larger than the decoded body (5 bytes), and the chunk decoder bills the
  wire bytes against `max_body` before decompression. The old finding's
  exact phrasing ("keeps any encoded-byte limit separate from the decoded-body
  limit") still stands.
- FIX: pass the limit to the chunk decoder as a separate `max_wire`-style cap
  (or `0` for "no separate cap") and keep `max_body` for the decoded
  invariant the pipe already enforces.
- CONFIDENCE: high — both arms reproduced in the same session from the same
  gzip bytes.

### B4. (R1-6) `zu_resp_abort()` on a fully-received but partially-read body is a no-op; reads continue

- SEVERITY: wrong-result (documented contract violation)
- LOCATION: `src/zuh_engine.c:861` — `zuh_open_body_abort()` returns
  immediately when `b->ended`, without recording `b->aborted`, and the read
  path then happily serves the remaining staged bytes.
- TRIGGER (reproduced): against `Content-Length: 5` + body `"hello"` with
  `stream = TRUE`: `zu_resp_read(r, 1L)` returns `"h"`; `zu_resp_abort(r)`;
  `zu_resp_read(r)` returns **`"ello"`** instead of raising
  `zu_cancelled_error`. (With close-framed bodies the abort path works, which
  is what the passing tests cover.)
- WHY: `ended` means *"finished receiving from the wire"*;
  `zuh_open_body_done()` already understands the difference between receiving
  and delivering, but the abort early-return treats either as "nothing to do".
- FIX:
  ```diff
  --- a/src/zuh_engine.c
  +++ b/src/zuh_engine.c
  @@ -861,7 +861,7 @@
   void zuh_open_body_abort(zuh_open_body *b) {
  -    if (!b || b->ended || b->aborted || b->failed) return;
  +    if (!b || b->aborted || b->failed) return;
  +    if (b->ended && b->staged_off == b->staged.len) return;   /* delivered */
  +    if (b->ended) { b->aborted = 1; ...release as cancelled... }
  ```
  (i.e. aborted state must be recorded even when the wire is ended, if
  undelivered bytes remain; the release call is then already a no-op.)
- CONFIDENCE: high — reproduced exactly as documented in the old review.

### B5. (R1-7) A failed `Rf_allocVector()` in `C_zu_stream_read` leaks the native `got` buffer

### B7. (R2-3) A request body function returning only empty pieces evades the request timeout

- SEVERITY: wrong-result (timeout contract)
- LOCATION: `src/init.c:167` — the `src_next()` empty-piece loop checks
  interrupts between pieces but never the request deadline.
- TRIGGER (reproduced): `timeout = 0.3`, a body function returning `raw()`
  200 times with 4 ms sleeps: the request ran **1.0 s** and called the
  function **201 times** before erroring — 3x the budget, and call count
  grows without bound (101 calls was the old round's number; nothing changed).
- FIX: thread the attempt deadline into `src_ctx` (as `zuh_deadline`) and
  return `ZUH_ERR_TIMEOUT` from the empty-piece loop when it expires.
- CONFIDENCE: high — reproduced.

### B8. (R2-4) The retry loop aborts a streamed response before deciding that no retry is possible

- SEVERITY: wrong-result (response destroyed, then returned)
- LOCATION: `R/perform.R:532-537` — `zu_resp_abort(resp)` still runs *before*
  `left <- deadline_at - ...; if (left <= 0 || delay >= left) break`.
- TRIGGER: staged not re-run this round (needs a two-attempt scripted native
  server; a mock does not exercise it because mock streamed responses carry a
  `read_state` cursor, not a native `stream`). Code order is unchanged from
  the earlier round's reproduction: a streamed 503 with a retry delay longer
  than the remaining budget is aborted and *then* returned; reading it raises
  `zu_cancelled_error` and the server's body is lost.
- FIX: check the budget (`left`, `delay`) before the abort, and only abort
  when a retry will actually happen.
- CONFIDENCE: medium-high — inspection plus the earlier round's live
  reproduction; re-confirm with a byte-scripted two-attempt 503 server.

### B9. (R2-5) Query parameters are silently dropped when the URL carries a fragment

- SEVERITY: wrong-result
- LOCATION: `R/url.R:93` — `url_with_query()` appends after the whole URL,
  inside the fragment, and picks `?`/`&` by scanning past it.
- TRIGGER (reproduced): with a byte-scripted server,
  `zu_get("http://host/path#section", query = list(x = "hello"))` — the
  server's request line is `GET /path HTTP/1.1` (no `?x=hello`); without the
  fragment the identical call produces `GET /path?x=hello`. The C URI parser
  correctly drops the fragment, so the parameter never reaches the wire, and
  nothing errors.
- FIX: split at `#` first, append the query to the pre-fragment part, choose
  `?`/`&` on that part, and re-attach the fragment (or refuse fragments in
  request URLs).
- CONFIDENCE: high — reproduced from the server's own received bytes.

### B10. (R2-6) `zu_resp_method()` reports the original method after a 303 rewrite

- SEVERITY: wrong-result (documented accessor contract)
- LOCATION: `R/perform.R:445` — `resp$method <- r$method` records the
  caller's original method; the engine's post-rewrite method is never carried
  back (`zuh_result` has no method field).
- TRIGGER (reproduced): `POST /start` answered `302` → engine follows with
  `GET /final`; the final response reports `zu_resp_method()` = `"POST"`
  while the doc block and §19.1 promise "the method actually sent".
- FIX: carry the final method out of `perform_hops` (it already holds the
  possibly-rewritten `method` local) — e.g. a `final_method` in
  `zuh_result`, set beside `out->status`, and read it in the transport.
- CONFIDENCE: high — reproduced via the package's own redirect origin helper.

## C. Clean areas (searched, not just skimmed)

- **The R↔C boundary (`src/init.c`)**: PROTECT/unwind discipline consistent on
  every path I traced, including the `src_ctx`/`cb_ctx` guard-token lifecycle
  and `R_PreserveObject` ordering; extern pointers are tagged and validated;
  NA/Inf coercion into C is bounded everywhere except the two R-layer gaps
  above. Direct `.Call` probes (NA strings, wrong types, huge values) were
  answered with correct error messages, not guesses.
- **Header framing** (§18.1): duplicate CL, CL+TE, non-`chunked` TE, obs-fold,
  oversized header blocks, truncated bodies, surplus bytes, 1xx/103, HEAD/204
  semantics — all behave correctly under scripted bytes.
- **Decoding** (§21): true gzip, zlib-wrapped deflate, raw deflate,
  concatenated gzip members, truncated streams, decompression-bomb caps —
  all correct (note: R's own `memCompress(type = "gzip")` emits a **zlib**
  stream, 0x78 0x9c — any reproduction fixture must use real `gzip(1)` output).
- **HTTP/2** (§65): 20 MiB streamed upload arrives byte-ordered over h2c;
  pulled bodies respect `n`; pooled h2 reuse works; trailers arrive with
  `TE: trailers`; abort keeps the connection for the next stream. The full
  live h2 suite passes against hypercorn.
- **Vendored code**: all `zuhttp:` patches verified against VENDOR
  documentation (13 `abort()` → error returns, the DEBUGBUILD-gated map
  printer); picohttpparser and the uriparser subset are unmodified upstream.
- **Build/registration**: 22-arg `C_zu_perform` registered with an exact
  22-arg signature; every `.Call` name registered; `R_forceSymbols(TRUE)` is
  actually enforced; Makevars uses `$(C_VISIBILITY)`, no `-w`, object lists
  in sync; `NDEBUG`/`NGHTTP2_STATICLIB` applied as documented.
- **Pool (§26)**: key completeness, per-field comparison, fork guard on idle
  connections, stale probes, capacity eviction — verified live (webfakes
  keep-alive) and by ctest.
- Fuzzing across the parsers (33,000 ASan/UBSan mutants) found nothing; the
  long-vector (>2 GiB body) and `max_body == body size` boundary cases are
  handled exactly.

## D. The five most severe findings, ranked

1. **A1** — mid-size HTTP/1.1 uploads are sent twice (connection poisoned
   with a garbage second request). `src/zuh_engine.c:1182`.
2. **B1/R1-2** — open streamed bodies bypass fork protection; a forked child
   leaves the parent's response permanently broken. `src/zuh_engine.c:861`,
   `src/zuh_net.c`.
3. **A2 + A3** — oversized `redirects` / `attempts` silently disable
   redirects or break every request on a client (same root cause: int-range
   coercion without `zu_pool()`'s guard). `R/perform.R:111,309`, `R/retry.R:78`.
4. **B2/R1-4** — repeated `Content-Encoding` fields silently hand back
   still-compressed bodies with the evidence removed. `src/zuh_body.c:28,45`.
5. **B4/R1-6 + B9/R2-5** — `zu_resp_abort()` is a no-op when bytes remain
   undelivered; query parameters silently vanish on fragment URLs.
   `src/zuh_engine.c:861`, `R/url.R:93`.

(R2-1 — the OpenSSL retained-configuration lifetime — would rank second if
the Linux build is in the ship path; it was verified by inspection only.)

## E. Edge-case test inputs to run through the package

R-side (native transport, `check = FALSE` unless noted):

- Policy boundaries: `redirects` and `zu_retry(attempts)` at
  `.Machine$integer.max` and one past it (A2/A3); `redirects = 0`;
  `max_body` equal, one below, and one above the decoded body size, under
  *both* framings (B3); `max_body = Inf`, `NaN`, `0`, `1e-4`;
